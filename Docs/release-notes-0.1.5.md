# SwiftDown 0.1.5

## 修复：冷启动时应用「起不来」、双击文件转圈报 -1712

现象：退出应用后双击 `.md`，有时转圈十几秒才打开、甚至提示「无法打开」；应用自己倒是能起，
但窗口出来得慢，日志里还能看到一段没有任何输出的空档。

### 根因：文件读盘压在主线程的启动阶段里

冷启动时打开一次文件，`open(2)` 这个系统调用本身可能被卡住很久。**实测过一次 6KB 的 markdown
耗时 5327 毫秒**，主线程采样 47 次全部落在内核的 `__open` 上；同一个文件从终端直接读只要 0.2 毫秒。
也就是说慢的不是解析、不是渲染，是这个上下文里的文件打开动作。

而 0.1.4 的会话恢复是**串行、同步**跑在启动阶段的：有几个标签就有几次这样的坑。
启动阶段被拖长的直接后果是 `didFinishLaunching` 迟迟不返回——系统要等应用「启动完成」才会投递
打开文件的事件，发送方（访达 / `open -a`）等 30 秒没有应答就报 `-1712`。

### 改法

1. **读盘离开主线程**。打开文件改成「后台读内容 → 主线程装配标签」，主线程不再碰文件系统。
   同一个文件连点两下不会打开两份，多选打开仍然按选择顺序排标签。
2. **会话恢复拆两段**。启动阶段只读会话元信息（几百字节，布局要在窗口出现前定下来，否则会先按
   默认布局画一遍再跳）；文档内容等**首帧之后**再读，读盘依旧在后台。
3. **启动时用户点谁就看着谁**。之前双击文件启动时，会话恢复结束时会把活跃标签切回「上次退出时
   的那份」，用户点的那份被挤到后面。现在主动打开的会排到最后并保持活跃。

## 效果（同一台机器实测）

| 指标 | 0.1.4 | 0.1.5 |
|---|---|---|
| `didFinishLaunching` | +388ms | **+329ms** |
| 窗口首帧 | +498ms | **+366ms** |
| 运行中打开文件 | 90ms | **77–86ms** |
| 窗口 `isVisible` 掉 0 的次数 | 0 | 0 |

更关键的是抗阻塞能力。用「打开一个没有写端的 FIFO」构造永久阻塞的读盘，此时再打开另一个文件
仍然是 **95ms 返回**，看门狗全程零次主线程阻塞记录——换作 0.1.4 的同步读盘，整个界面会一起卡住。

## 顺带

- 新增启动时间线探针 `LaunchProbe`：以**进程启动时刻**为基准打点，并用**独立线程**的心跳看门狗
  监测主线程，卡住时能从别的线程读出主线程停在哪个函数。仅在 `/tmp/swiftdown-trace.on` 存在时启用，
  正常使用零开销。这类问题以后能直接看到数字，不用再猜。

## 自检

82 项全 PASS（0.1.4 为 80 项）。新增 2 条：

- **打开文档的读盘不在主线程同步完成**：`open` 返回时标签还没挂上，说明读盘确实是异步的。
  有人改回同步读盘时这条立刻 FAIL——而那种改动只有在系统刚好卡住文件打开时才会暴露。
- **启动阶段只读会话元信息、不读文档**：`init` 之后标签数必须为 0，内容在恢复阶段才出现。

## 安装

下载 `SwiftDown-0.1.5-arm64.dmg`，拖进「应用程序」。首次打开若提示无法验证开发者，
右键 → 打开，或执行：

```bash
xattr -dr com.apple.quarantine /Applications/SwiftDown.app
```

仅 Apple Silicon（arm64），macOS 13+。
